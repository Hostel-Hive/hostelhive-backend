# Excel report exports - issue #85

Implements the Excel portion of SRS FR031 using existing attendance (#78), leave
(#81) and complaint (#83) report semantics. PDF and CSV exports are excluded.

## API contract

Active Admin/Warden only, using existing Firebase/local account authorization:

| GET route | Allowed optional filters |
|---|---|
| /api/v1/reports/attendance/export | student_id, direction |
| /api/v1/reports/attendance/daily/export | student_id, direction |
| /api/v1/reports/leaves/export | student_id, status |
| /api/v1/reports/complaints/export | student_id, category, status |

Every route requires inclusive hostel-local from/to dates, exactly YYYY-MM-DD,
with at most 366 selected calendar dates. Student ID is an optional canonical
lowercase nonzero profile UUID. Direction is IN/OUT; leave status is
pending/approved/rejected; complaint status is pending/in_progress/resolved;
category is maintenance/disciplinary. Values are case-sensitive.

The same calendar conversion, source filters, ordering and current staff authority
checks serve JSON reports and exports. Attendance selects recorded scan times;
leave/complaint reports select submission dates. Status is CURRENT at the query
snapshot, not historical status on a past date. Resolution/decision times can be
outside the selected submission period. Archived/inactive Student history and
disabled scanner history remain included. Photos and source workflows are unchanged.

Exports deliberately have NO pagination parameters. Omit limit and offset;
even limit=20 or offset=0 is invalid. Unknown, duplicated, empty or malformed
parameters, wrong-route filters, invalid/reversed/oversized date ranges, invalid
UUID/status/category/direction, and bodies on GET return HTTP 400 invalid_report_query.
There is no format selector: these dedicated endpoints return .xlsx only.
Existing paginated JSON APIs retain their original limits and behavior.

## Limits, consistency and failure behavior

The maximum is 5000 DATA ROWS per file, excluding headers/Summary. Daily attendance
has at most 366 rows because each selected date appears, including zero-activity
days; its underlying movement summary may count many more scans.

The service validates the same report filters, then asks the existing repository
for a single bounded snapshot with up to 5001 rows. Rows and full-period totals
come from ONE SQL statement snapshot, not sequential JSON pages. A successful
file contains ALL matching rows within the limit. Over 5000 returns HTTP 413
report_export_too_large and NO workbook: narrow the date range or other filters.
There is no silent truncation, partial export or asynchronous export job.

The backend permits two active Excel requests across all four export routes per
ExportAPI instance (one shared instance in application wiring). Further requests
receive HTTP 429 report_export_busy; retry after an active export finishes. This bounds
simultaneous workbook generation/download work rather than imposing a time-based
user rate limit. The existing ACCOUNT_MANAGEMENT_TIMEOUT (default 8s) bounds query
and generation; HTTP_WRITE_TIMEOUT defaults to 15s. Keep HTTP write timeout longer
than authentication plus export work when customizing deployment settings.

Unauthorized requests return HTTP 401; authenticated disallowed/inactive roles return HTTP 403.
Student, Sub-Warden and Security cannot export, including maintenance-only exports.
Current staff authority is rechecked under the existing users-table lock during
the source read. Workbook rendering happens after the read transaction completes;
a downloaded file is a local copy, not a revocable live dashboard subscription.

Database/encoding/deadline failures return HTTP 503 service_unavailable. Workbook
construction finishes in memory BEFORE download headers are written, so failed
generation returns JSON rather than a broken XLSX with a success response.
Successful responses have:

- Content-Type: application/vnd.openxmlformats-officedocument.spreadsheetml.sheet
- Content-Disposition: attachment; filename=hostelhive-<kind>-<from>-to-<to>.xlsx
- Content-Length matching the generated bytes
- Cache-Control: no-store
- X-Content-Type-Options: nosniff

Errors also use no-store. The server creates no application export files or public
URLs. A caller can save the returned attachment locally. The row cap is not an
Excel worksheet capacity limit; it is this synchronous API's resource boundary.

## Workbook contents

Each file has two sheets:

1. Summary: report name, applied dates/timezone/filters, date/status interpretation,
   blank-value meaning, matching/exported row counts, export cap and full-period
   summary metrics. Omitted optional filters display All.
2. Data: every matching record in the same order as the JSON report, with column
   headers, frozen first row, column filters and wrapped text.

Attendance movement rows preserve event/device/Student IDs, direction, recorded
time and originally recorded permission/incident references. Unspecified legacy
access results remain blank; they are not treated as approved or not_required.
Cooldown/already-IN/already-OUT attempts are excluded. Daily rows include zero
counts and retain whole-period distinct Students rather than summing daily counts.
Daily Total Matching Rows counts dates; other export row totals count records.

Leave rows include leave/request/Student/submission IDs, requested dates, reason,
status, submission time, decision time/actor/note. Pending decision fields remain
blank. Complaint rows include source details/version and Resolution Recorded,
resolution update/time/actor/note. Reopened and legacy unspecified resolutions
have No with blank resolution fields. Re-resolved complaints use the current
recorded audit resolution. Missing facts are never inferred.

Complaint Summary contains status and category breakdowns of the SAME population.
Each breakdown sums to Total Matching Rows; do not add both breakdowns together.
Every filter affects data and all summary metrics, independently of JSON pagination.

Timestamps are RFC3339 TEXT in the configured hostel timezone, preserving the
original absolute instant and offset. They are not timezone-less Excel date
serials. IDs and versions are text to preserve leading characters and integer
precision. Ordinary counts are numeric; integers beyond Excel's15 significant
numeric digits are stored as exact decimal text rather than being rounded.

All text, including descriptions/reasons/notes starting with =, +, -, @, tabs or
apostrophes, is explicitly written as literal string cells. Text is not converted
to formulas or hyperlinks, and content is not changed by prefixing apostrophes.
No macros, external links or spreadsheet formulas are generated. This safety claim
applies to the typed .xlsx output, not a later conversion by another program to CSV.
Credentials, QR data/hashes, contact/guardian information, image IDs, private R2
keys/hashes and direct photo links are excluded. Existing photo APIs retain their
own permission checks. Exports do not update attendance, decisions, resolution
history, images, notification delivery/read state or Firebase projections.

## Architecture and deployment

New report export domain records/DTO, service and handler follow existing layer
boundaries. Services reuse report filter validation and existing repository query
interfaces; no cross-module concrete repository import or copy of source SQL.
Excelize v2.11.0 is pinned in go.mod/go.sum. The workbook implementation lives in
internal/platform/spreadsheet behind the ExcelWorkbookWriter service port.
Architecture checks disallow Excelize imports in handler/service/domain/DTO layers.
Coverage evidence includes both report and the spreadsheet adapter.

No migration or new production environment variable is needed; schema 24 suffices.
Build/restart the backend to load the four routes. Existing R2/RTDB configuration
is unchanged. No Node/npm startup tooling is included in this ticket.

New-Item -ItemType Directory -Force artifacts | Out-Null

Invoke-WebRequest -UseBasicParsing -Uri "${exportURL}?${exportQuery}" `
    -Headers $adminHeaders -OutFile artifacts/complaint-report.xlsx
