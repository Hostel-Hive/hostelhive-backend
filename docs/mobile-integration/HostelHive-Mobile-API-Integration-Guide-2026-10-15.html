1. Read this first

  1. Flutter authenticates with Firebase Authentication. There are no Go /auth/login, /auth/forgot-password, /auth/reset-password or /auth/logout endpoints.
  2. Every business API path starts with /api/v1. Send a Firebase ID token as Bearer.
  3. /me returns account metadata. Use /me/student-profile for the Student profile, guardians, current room/bed and scan-based presence.
  4. Extended leave and late access are separate models and endpoints. There is no /passes endpoint, 18-day quota, Going Home endpoint or cancellation endpoint.
  5. Complaints are created as JSON. Photos upload separately as image bytes. Maximum THREE attached photos, not five; title and severity are unsupported.
  6. The inbox is /notifications. Read state is read_at, not is_read. There is no notification-detail GET or mark-all-read endpoint.
  7. Approval authorizes a trip; it never changes attendance. Only accepted scanner movements establish IN/OUT. Do not change presence optimistically in Flutter.
  8. Backend APIs enforce ownership. Do not give the mobile app Admin credentials to work around missing Student APIs.

2. Connection, headers and data conventions

2.1 Base URL

Set one environment-specific API base URL ending in /api/v1, for example:

API_BASE_URL=https://YOUR_VERIFIED_API_HOST/api/v1

This is a PLACEHOLDER, not an available deployment. Use it consistently; do not append /api/v1 twice. Store configuration outside individual repository methods.

The backend owner's PC currently uses http://127.0.0.1:18080 for local testing. On a physical phone, 127.0.0.1 refers to the PHONE, not the PC. A reachable backend address and appropriate network configuration are required for phone-to-API tests. A working Firebase connection alone does not make the local Go server reachable. Use a team-approved HTTPS endpoint for shared integration; do not ship a development cleartext exception or disable certificate verification in production.

2.2 Authentication and content headers

For JSON writes:

Authorization: Bearer FIREBASE_ID_TOKEN
Accept: application/json
Content-Type: application/json

For JSON GET/empty POST/DELETE, omit Content-Type if there is no body. Send no body, not even {}, on endpoints documented as empty-body requests.

For image upload use image/jpeg or image/png, and send the file bytes directly. For QR/photo downloads accept image/png or the applicable image media type; always check the HTTP status and Content-Type before attempting to display bytes.

2.4 JSON and timestamps

  • JSON property names are snake_case and enum strings are case-sensitive.
  • Objects are returned directly; there is no universal data/success wrapper.
  • Parse unknown response fields tolerantly. Send ONLY documented request fields; unknown write fields and unsupported/repeated query parameters are rejected.
  • For timestamp fields, use RFC3339 with an explicit timezone: 2027-01-15T09:00:00+05:30 or 2027-01-15T03:30:00Z. Do not send date-only or timezone-free strings for timestamp fields. The history endpoint in section4.4 instead accepts calendar-date filters as YYYY-MM-DD.
  • Parse timestamps into DateTime values; compare instants rather than formatted strings. The backend may return another offset for the same instant.
  • The default hostel policy timezone is Asia/Colombo. Flutter device timezone is not authoritative for permitted gate hours. Ask the backend owner if policy changes.
  • Null means no value yet. Optional response fields may be absent. Do not replace null dates/IDs with invented defaults or assume missing presence means OUT.
  • User-entered text is plain text, not trusted HTML. Render it as text.

2.5 Pagination

Most collection responses use:

{
  "items": [],
  "total": 0,
  "limit": 20,
  "offset": 0,
  "has_more": false
}

Default limit 20; supported range 1-100; offset must be >=0. total is the number of matching records, not the number on this page. Stop when has_more is false; next offset is current offset plus received item count. Avoid an endless loop if an unexpected empty page arrives. Reset offset to0 when changing filters/refreshing.

Each request reads current data, not a frozen multi-page session. New records may shift offset pages; deduplicate by stable ID and support refresh. Do not append a repeated page after retry. Photo lists and push-device lists have their own shapes.

2.6 Error responses

Handled API errors normally have:

{"error":"invalid_input"}

There is no guaranteed human-readable message or per-field error list. Map known codes to clear UI text, retain an unknown-error fallback and never display raw HTML or internal diagnostics. Router/proxy errors, including unmatched404/405, may be plain text; do not assume every non-2xx response is JSON.

HTTPClient behavior

The same error code can represent multiple business conflicts. The server does not currently provide an 18-day quota error, ALREADY_OUTSIDE error or the proposed 422 past-departure response.

3. Firebase authentication and session lifecycle

3.1 Project and responsibility

Use Firebase project hostel-hive-152ef. Configure Firebase in the Flutter app with its existing registered application. Firebase owns passwords, reset emails and client token refresh. The Go API verifies ID tokens and checks the current local role/status on every request. A valid Firebase account by itself does not create a HostelHive local account/profile or grant Student access.

Accounts are provisioned through the agreed Admin workflow. Do not add public self-registration merely because the Firebase SDK supports creating an account. No service-account JSON, R2 secret or scanner credential belongs in the mobile app.

3.2 Sign in, then verify application access

Flutter SDK sketch (merge into the existing AuthRepository):

final result = await FirebaseAuth.instance.signInWithEmailAndPassword(
  email: email.trim(),
  password: password,
);
final idToken = await result.user!.getIdToken();
if (idToken == null) {
  throw StateError('No Firebase ID token was returned.');
}
// GET API_BASE_URL + '/me', Authorization: Bearer idToken.
// Enter the Student app only after /me succeeds and role == 'student'.

Do not trim or change the password. Student-ID login is not implemented; use email. The SDK result is not the proposed backend {token, student} response. Store the /me account separately from Firebase's User object and the /me/student-profile response.

A revoked/expired/disabled token normally produces401; a valid Firebase identity without an active eligible local account produces403. A transient account lookup failure can produce503 service_unavailable. Wrong-role users must not enter the Student workflow even if their Firebase sign-in succeeded.

Reference: Firebase Flutter email/password authentication.

3.3 Restore session and refresh

Use Firebase's authentication state to restore its signed-in user, obtain a current ID token and call /me again. Do not assume persisted account metadata still grants access. Retrieve tokens through the SDK rather than persisting a bearer string forever. Keep account-specific caches scoped to the active account.

On an API401, try getIdToken(true) once and retry the same request once. For a mutation, retain the SAME request_id/image_id and canonical body. Persistent401 requires sign-in; repeated403 requires handling account/role access. Do not silently refresh forever or retry a decision/create with a new UUID.

Reference: Firebase Flutter User.getIdToken.

3.5 Admin-approved initial setup (#95)

Admin registers an approved university email and profile, individually or through /student-invitations/import. The worker sends a private Firebase-hosted password setup/reset email. These are Admin operations, not mobile self-registration. The Student opens the email and chooses their own separate HostelHive password. Admin does not know it. Do not request a university-issued password or implement SSO. Use the hosted Firebase action page; no Go API accepts the new password or returns an Admin-copyable action link. General later password recovery remains Firebase.

After choosing the password:

  1. Sign in through Firebase Email/Password and obtain the current ID token.
  2. Call /me. If setup_required is true, stop normal feature loading, including profile, QR, inbox and push registration. They return403 setup_required.
  3. Send POST /api/v1/me/setup/complete with the Bearer token, no query and no body (not {}). Success200 contains setup_required:false and setup_completed_at.
  4. Refresh /me, then proceed with the current-role/profile checks and API calls.

Example success (fictional timestamp):

{"setup_required":false,"setup_completed_at":"2026-10-16T10:00:00Z"}

The backend checks the reserved UID, approved email, current eligibility, unrevoked password sign-in and Firebase password-update metadata newer than the committed bootstrap baseline. Password sign-in/reauthentication must be within five minutes and at/after that password update. A forced token refresh alone does not update Firebase auth_time. On409 setup_not_verified, complete the hosted setup or freshly sign in/reauthenticate with the chosen password and retry once. Never set a local completion flag to bypass this response. Do not loop password resets automatically. On503 preserve pending state and offer a bounded retry/contact Admin. Inactive or archived accounts cannot complete setup; password setup does not reactivate them.

Completion is idempotent and preserves the first completion timestamp. A legacy eligible Student with no invitation gets false/null; existing accounts are not forced through this flow. In /me, false setup_required is omitted; absent means false. The completion response always includes the boolean.

Provider email acceptance is not proof of receipt. Firebase handles expired/used action-code errors on the hosted page. Offer contact/resend through the authorized Admin; do not promise a code lifetime or resend invalidation. Real email receipt, action-code handling and Flutter integration remain unverified in this snapshot.

Backend prerequisites: migration26, STUDENT_INVITATIONS_ENABLED=true, approved STUDENT_EMAIL_DOMAINS and Firebase Authentication/IAM email configuration. With the flag off, pending accounts stay blocked and setup completion returns503. No server credentials belong in Flutter. See [the full Admin contract](../student-invitations.md) for registration, bulk outcomes, cooldown, retries and operational rollback.

Reference: Firebase Flutter user management.

A missing/archived/ineligible profile can give 404 not_found; auth403/401 and student_profiles_unavailable503 are also possible. Respect Cache-Control:no-store; clear displayed private data on logout/account switch. No Student QR rotation API.

4.4 Own recorded attendance history (#93)

GET /api/v1/me/attendance/events?from=2026-10-01&to=2026-10-16&direction=IN&limit=20&offset=0
Authorization: Bearer FIREBASE_ID_TOKEN

Active Students with an unarchived profile only. Ownership is derived from the verified login. Do not send student_id or user_id. GET body must be empty. This is a read-only history of accepted, recorded movements. Cooldown and already-IN/already-OUT attempts are excluded. Repeated recorded movements, if present in legacy data, are preserved as distinct records rather than inferred or removed by the reader. Approval, permission consumption and current presence are not changed by reading this endpoint.

QueryRules
from and toOptional together; strict YYYY-MM-DD, both inclusive hostel-local dates. Start must not follow end. Maximum 366 calendar days; supported years 0001 through 9998. If neither is supplied, page through all own recorded history.
directionOptional, case-sensitive IN or OUT. Omit to include both.
limitOptional integer, default 20; minimum 1, maximum 100.
offsetOptional integer, default 0; minimum 0, maximum 1000000.

Empty, repeated, unknown or malformed query parameters return 400. An isolated from or to is invalid. Client timezone parameters are not accepted; use the configured hostel timezone returned in the page (normally Asia/Colombo). The server translates the inclusive date range to local start-of-day through start-of-day AFTER to, using an exclusive upper bound. For example, 2026-10-15 in Asia/Colombo covers 2026-10-14T18:30:00Z inclusive through 2026-10-15T18:30:00Z exclusive. Calendar boundaries respect timezone/DST rules.

Success 200, direct JSON:

{
  "items": [
    {
      "movement_id": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
      "event_id": "11111111-1111-4111-8111-111111111111",
      "direction": "IN",
      "occurred_at": "2026-10-15T09:00:00+05:30"
    }
  ],
  "total": 1,
  "limit": 20,
  "offset": 0,
  "has_more": false,
  "timezone": "Asia/Colombo",
  "from": "2026-10-01",
  "to": "2026-10-16"
}

items is always an array, including [] when empty. total counts all matching recorded movements, not just the current page. No matches, or an offset beyond the last page, return 200 with an empty items array and has_more false; total still describes all matching rows. from/to are null when dates are omitted.

movement_id is a stable opaque 64-character lowercase hexadecimal identifier. Use it as the Flutter list/deduplication key. event_id is the scanner event UUID; it is unique within a scanner, so event_id alone must not be treated as a globally unique list key. No scanner/device identity or credentials, payload hashes, processing outcomes, access results, permission or incident references are returned.

occurred_at is an RFC3339 timestamp; parse the instant and display it in the hostel timezone. Results sort by occurred_at descending, then the internal composite event key descending to resolve ties. Each page's count and items use one read-only repeatable-read database snapshot. Offset pages are stable while the dataset is unchanged. New scans between separate page requests can shift positions; refresh/reset pagination and merge by movement_id when appropriate.

ResultMeaning

6. Late-access requests: early exit or late entry

6.1 Model and hostel hours

A request authorizes ONE expected movement in a specified direction. It is not an extended leave interval, round-trip pass or destination record.

Default Asia/Colombo policy:

MovementNeeds permission
OUT before 06:00Yes: early exit
OUT at/after 06:00, including after 20:00No, under this specific policy
IN from 06:00 until just before 20:00No
IN at/after 20:00 or overnight before 06:00Yes: late entry

The backend rejects a new late-access request for a time/direction that does not require permission. Hours are configurable; these are defaults, not a guarantee about every deployed environment. Display hostel-local time clearly in the app.

6.4 Matching, conflicts and approval

An approved permission can be consumed by one recorded movement of the same Student/direction within 30 minutes before/after the expected time. A second scan is not automatically a second authorized use. Approval/notification is not proof that the Student physically moved. A suppressed duplicate scan does not consume another permission. Without a matching permission, a restricted movement is still recorded and an incident is created for staff; mobile must not describe approval as a remotely opened door or backend denial as a physical gate lock.

Two active requests cannot use the identical Student/direction/expected-time combination. Exact request_id retries return the original record; changed reuse conflicts. Distinct expected times can coexist. Rejected requests allow a replacement.

8. Private complaint photos

8.1 Limits and upload sequence

Maximum 3 active/reserved attachments per complaint. Each input must be nonempty JPEG/PNG <=5,242,880 bytes (5MiB), <=4096 pixels in either dimension and <=12,000,000 pixels total. MIME type must match the actual decoded format. HEIC/WebP/GIF/SVG, base64 JSON and multipart wrappers are unsupported. Convert/compress locally as needed and preview the final intended JPEG/PNG before upload.

The backend decodes/re-encodes approved images, strips embedded metadata and uses JPEG quality 85/PNG re-encoding. Do not assume downloaded bytes, embedded EXIF or size_bytes equal the original file. A normalized image that exceeds limits is invalid.

  1. Create the Complaint first and retain complaint_id.
  2. Generate/retain one image_id per selected photo.
  3. PUT the bytes to its endpoint, preferably sequentially for this small cap.
  4. Track each photo's result; show partial success clearly.
  5. GET current image list and complaint version after uploads.

Complaint creation and photo uploads are separate commits. If photo2 fails, the complaint and photo1 may already exist. Do not create a second complaint on retry. There is no server-side unsubmitted complaint/photo draft; pre-submit preview is local. Do not pretend leaving the screen rolls back committed uploads.

11.5 Flutter lifecycle

  • Configure Firebase Messaging for the same Firebase project, obtain OS permission, then obtain the FCM token. For iOS, configure APNs/capabilities and wait for its token as required by the SDK. Use the Android setup first for this handoff test.
  • After successful application login, register the installation token for THAT account.
  • Subscribe to token refresh and PUT new tokens with the same installation UUID. Coordinate async callbacks with the current auth session; an old-account callback must not register its token after another account has logged in.
  • Before account switch/logout, DELETE the old account registration, then delete/ rotate the SDK FCM token and clear account data. If offline cleanup fails, record the limitation and delete the local SDK token; do not reuse the old token under the next account. Device registration may409 until ownership is safely cleared.
  • Handle foreground messages, background notification display and both cold-start and background notification taps. Foreground display requires explicit handling.
  • On tap, use the CURRENT account to refresh its inbox. Match notification_id to an authorized item and navigate using that source reference. Drop inaccessible IDs; do not treat push as permission or open another account's cached detail.

The payload uses generic visible text:

{
  "notification": {
    "title": "HostelHive",
    "body": "You have a new notification. Open HostelHive to view it."
  },
  "data": {
    "notification_id": "88888888-8888-4888-8888-888888888888",
    "source_type": "leave"
  }
}

This shows the logical message content, not the complete SDK RemoteMessage envelope. Do not expect leave_id, decision reason, Student name or private source details inside push data. Use the inbox item. Device-level duplicate delivery is possible; deduplicate client handling by notification_id. Android tags/APNs collapse IDs help but do not guarantee exactly-once display. A generic already-accepted message can arrive after logout; source retrieval must still require current authorization.

The backend retries transient failures with bounded backoff and honors longer Retry-After; jobs expire one hour after the event. FCM acceptance is not phone receipt, reading or a physical movement. 14.1 Retry rules

Maintain logical operation states such as editing, submitting, outcome_unknown, confirmed and conflict. Disable accidental repeated taps while a request is in flight, but rely on backend operation identity for network retries.

OperationStable retry identityWhat not to change on a retry
Create leaverequest_id within StudentDates and reason
Create late accessrequest_id within StudentDirection, expected_at and reason
Create complaintrequest_id within StudentCategory and description
Add complaint noterequest_id within actor/complaintexpected_version and text
Upload photoimage_id within complaintFile content and MIME type
Mark notification readnotification_idNo body; original timestamp is retained
Register pushaccount plus installation device_idSame token/platform for an exact refresh; new token is an intentional update
Delete photocomplaint_id plus image_idNo body; never reuse removed image ID for a new upload

A changed form is a NEW operation; generate a new request_id after user confirmation. When recovering a saved draft after process death, preserve the operation UUID/body securely if automatic retry is offered. Do not replay another account's draft. Never label a timeout as definitely failed if the server might have committed.

14.2 Cache, media and state freshness

  • Scope memory/disk data to the local account, clear it on account switch and honor no-store responses. Do not persist private QR/photo bytes in a shared global cache.
  • Fetch image bytes with the current Authorization header and check status first. JSON error text is not a corrupted image; surface the actual failure.
  • Keep loading, empty, unavailable and permission-denied states distinct. An empty list is not the same as a failed request or a Student who is outside.
  • Student account active state and unarchived-profile eligibility are different. Account login can succeed while a new leave/QR/photo operation is not eligible.
  • Ownership404 should not reveal another Student's record. Do not enumerate IDs or use admin tokens to make that404 disappear.
  • Refresh private data after successful changes and when the app resumes as needed. A local notification/read update is not a write to attendance or room allocation.

15. Using the accompanying Postman collection

File: HostelHive-Mobile-API-2026-10-15.postman_collection.json. The collection contains 29 implemented Student-facing requests, grouped by feature; it does not add the missing proposed routes or perform Firebase password login.

  1. Import the JSON collection in Postman.
  2. Set collection variable api_base_url to the actual reachable API base ending /api/v1. The supplied hostname is deliberately a non-working placeholder.
  3. Obtain a TEST Student's Firebase ID token through the configured client/helper. Put it in a private LOCAL firebase_id_token value; never share/export a collection containing a real token. Refresh when expired; Postman does not run Flutter auth.
  4. Set leave_id, late_access_id, complaint_id, image_id, notification_id, announcement_id and push_device_id as needed. push_device_id is a retained UUID.
  5. Create-body request_id placeholders must be replaced with generated UUIDs. Keep those values for exact retries. Example future dates may need adjustment.
  6. For photo PUT choose a local JPEG/PNG as the binary body and set the matching media type. The collection defaults to image/jpeg; no file is bundled.
  7. Inspect responses and manually transfer returned IDs/version into local variables. No collection script silently creates accounts, changes roles, decides requests, writes database records outside the request you choose, or sends emails.
  8. Send one request at a time against dedicated test records. The collection includes mutations; do not run an uncontrolled collection runner on real Student data.

The Markdown and HTML guides are self-contained handoff copies. HTML opens in a browser and supports printing/searching/copying code. Share the guide plus collection; share environment URLs and test identities privately through the team's usual process.
