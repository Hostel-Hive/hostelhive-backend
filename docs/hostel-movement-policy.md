# Hostel movement policy (#118)

This contract supersedes the former ordinary leave approval and 18-day allowance
workflow. All comparisons use Asia/Colombo by default (the existing configurable
HOSTEL_TIMEZONE, HOSTEL_EXIT_OPENING=06:00 and HOSTEL_ENTRY_DEADLINE=20:00).

| Actual movement | Approval |
|---|---|
| IN or OUT from 06:00 inclusive until 20:00 exclusive | Not required |
| IN or OUT before 06:00 or at/after 20:00 | Admin/Warden approval required |

Students do not request approval for the trip itself, or submit an expected return
date for going home. A trip may span nights; each physical gate movement is
evaluated using its own actual scan time. Midnight to before06:00 is restricted.
Exactly06:00 is normal; exactly20:00 requires approval. A day-precision date alone
is never an early-exit or late-entry permission.

## Active APIs

- POST /api/v1/going-home: Student signing-book declaration, body only
  `{"request_id":"UUID"}`. The app displays "I am going home now". The authenticated
  identity and submission timestamp form the record; no description/date/time,
  destination or approval input is accepted. The fixed signing-book wording is
  UI text, not an additional stored free-text field. No staff notification is
  generated by this declaration. Existing known-IN, outstanding-intent, exact-retry
  and account eligibility rules are unchanged. First acknowledgement201; replay200.
- POST /api/v1/late-access-requests: one restricted movement, with `request_id`,
  `direction` IN/OUT, `expected_at` RFC3339 and `reason`. Supports early exits,
  late exits and overnight entries. Normal-hour and past submissions return400.
  Admin/Warden decision and Student pending cancellation endpoints remain active.
- Scanner attendance routes: only recorded scans update presence. Approvals never
  mark anyone IN/OUT and Going Home does not waive curfew. An unapproved movement
  still records physical presence and creates a staff incident, rather than
  pretending the physical movement did not happen or remotely unlocking a gate.

Existing permission consumption remains unchanged: nearest eligible unused,
direction-matching approval within inclusive +/-30minutes, decided by scan time,
consumed atomically once. A recorded arrival/departure just inside normal hours
can consume a matching approval. Ignored scans do not consume it. Scanner event
retries return persisted results even if the current policy has changed.

New OUT incidents at/after closing are `late_exit`; OUT before opening remains
`early_exit`; restricted IN remains `late_entry`. The incident filter and inbox
title support late_exit. Existing FCM attendance-incident delivery uses the same
durable event path; no additional recipient roles or notification types are added.

## Retired APIs and history

After existing login/role checks, these return HTTP410 with
`{"error":"leave_workflow_retired"}` and Cache-Control:no-store:

- POST /api/v1/leaves
- POST /api/v1/leaves/{leaveID}/decision
- POST /api/v1/leaves/{leaveID}/cancel
- GET /api/v1/me/leave-allowance

Retired routes do not parse or act on old payloads or replay keys. Missing/invalid
login remains401 and disallowed roles remain403. There is no replacement quota.
Clients must remove new ordinary-leave forms, approve/reject/cancel controls for
legacy leave, and the 18-day usage ring; they should explain410 rather than retry.
Pending legacy leave remains pending historical data, never auto-approved,
cancelled or converted into a movement permission.

GET /api/v1/leaves and /api/v1/leaves/{leaveID}, existing leave reports/exports,
historical inbox entries and GET /api/v1/me/passes remain readable with existing
ownership and roles. Combined history includes legacy leave and active late access;
Going Home is still excluded. Only pending late-access items offer cancellation.
No new Going Home staff list/detail endpoint or frontend changes are included.

## Deployment and rollback

1. Back up the target database and review the API-breaking change with clients.
2. Stop older API instances: they still permit ordinary leave writes and exempt
   nighttime OUT. This is a coordinated API/policy cutover, not a rolling mixed
   version deployment. Do not run a local old backend against the shared database.
3. Apply migration30 (`hostel_movement_policy`) with the pinned migration CLI.
4. Deploy the updated backend and compatible clients; check /ready and Swagger.
5. Test using dedicated accounts and test records, never fabricate real attendance.

Migration30 only expands the incident constraint. It does not delete or rewrite
leave, decisions, approvals, attendance, declarations, inbox/read state or queued
delivery. Older approved late-access records retain their decision/consumption
history. The old allowance calculator is retained internally for historical tests,
but its public endpoint is retired.

Rollback fails closed if late_exit incidents exist. Do not delete or relabel
real attendance to force rollback. Plan a forward repair instead. Code rollback
also restores the old policy, even if the schema allows it; it is not a neutral
operational rollback. No Supabase migration or Render deployment is performed by
implementing this source change.
